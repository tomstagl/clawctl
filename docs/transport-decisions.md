# Transport decisions

Every `clawctl` subcommand crosses one of three transports: the openclaw gateway's HTTP API, an SSH session to the gateway host, or a local-process call (`git`, `gh`, no network). The choice is load-bearing: picking the wrong transport leaks secrets, opens injection surfaces, or breaks the read-only-by-default principle (`docs/design-principles.md` §1).

This document records, per existing subcommand, which transport is correct and why. New subcommands should consult this matrix before being implemented; if a feature would require a different transport than its sibling, justify the divergence here first.

## Legend

- **Operation** — the `clawctl` subcommand and what it does over the wire.
- **Transport** — `HTTP API` (gateway `/v1/*` and `/health`), `SSH` (`ssh $CLAWCTL_SSH_HOST -- …`), or `Local` (no network: `git`, `gh`, filesystem checks).
- **Rationale** — why this transport, citing the design principle it satisfies.
- **Alternative considered** — the runner-up transport and the concrete reason it lost.
- **Failure mode avoided** — the specific, named failure the chosen transport prevents (not a generic "more secure").
- **Exit-code contract** — exit codes the subcommand documents and is required to honor (see `clawctl help`).

The exit-code vocabulary is shared across all transports: `0` ok, `2` usage error, `6` DNS, `7` connection refused, `22` HTTP 4xx/5xx, `28` timeout. `1` is reserved for `verify`'s "not found" semantics.

## Matrix

| Operation | Transport | Rationale | Alternative considered | Failure mode avoided | Exit-code contract |
| --- | --- | --- | --- | --- | --- |
| `health` — GET `/health` liveness probe | HTTP API | The gateway already exposes a public liveness endpoint; it is the cheapest path that proves end-to-end reachability of the data plane (auth + transport + gateway + upstream). Read-only, no mutation surface (principle §1). | SSH ping (`ssh $CLAWCTL_SSH_HOST true`) only proves SSH works, not that the gateway is up; it would mask a half-down service. | False-positive "all green" when the gateway daemon is down but the host is fine. | `0`, `6`, `7`, `22`, `28` |
| `models` — GET `/v1/models` with 60s file cache | HTTP API | The agent slug list lives in the gateway's `/v1/models` response and rotates with deploys. Caching client-side (`$CLAWCTL_CACHE_DIR/models.json`, TTL `$CLAWCTL_MODELS_TTL`) keeps the slug-validator fast without holding stale tokens. Cache misses fail open with a stderr warning so the wrapper never blocks transport on metadata. | Hardcoded slug allow-list in the wrapper would require a release per agent change; `clawctl cli openclaw agents list` over SSH would work but adds a roundtrip and an SSH dependency to a read-only path. | Stale slug rejections after a gateway agent rename or rollout — and a hard failure on any local `clawctl msg` call when the cache is unreachable. | `0`, `6`, `7`, `22`, `28` |
| `msg` — POST `/v1/chat/completions`, non-streaming | HTTP API | The OpenAI-compatible chat endpoint is the only contract the gateway publishes for inference; bearer auth from Keychain (principle §2) and a per-call `traceparent` header (§3) attach to every request. The response body flows through `_redact` before reaching stdout (§4). | `clawctl cli openclaw msg …` over SSH would sidestep the gateway's auth/rate-limit/observability layer, defeating the point of having a gateway. | Bypassing gateway-side rate limits, audit logs, and the redaction-at-the-boundary contract. | `0`, `6`, `7`, `22`, `28` |
| `stream` — POST `/v1/chat/completions` with `stream: true` | HTTP API (SSE) | Streaming is part of the same `/v1/chat/completions` contract and reuses bearer auth plus `traceparent`. The wrapper deliberately buffers the full SSE response to a tempfile before parsing and redacting, because regex-based redaction is unsafe across chunk boundaries (a secret split between two `data:` frames could otherwise leak). The latency cost is accepted to keep §4 intact. | A streaming-redactor pipeline would lower latency but cannot guarantee boundary-safe masking without a stateful state machine — out of scope for a bash wrapper, and would re-introduce the leak the redaction layer exists to prevent. | Boundary-split secrets escaping `_redact` because the regex matched across two SSE chunks. | `0`, `6`, `7`, `22`, `28` |
| `raw METHOD PATH` — arbitrary authenticated gateway call | HTTP API | An escape hatch for endpoints not yet wrapped (e.g. probing new gateway routes during development). Same auth (`_token`) and same `traceparent` as every other HTTP call (§3). Retries are applied only on `GET` to avoid replaying mutating writes. | Telling users to construct `curl` commands by hand would force them to look up the Keychain service name and replicate the redaction pipeline — the exact things the wrapper exists to centralize. | Token leakage into shell history (when users copy bearer tokens into ad-hoc curl commands) and untraced calls that don't show up in Jaeger. | `0`, `6`, `7`, `22`, `28` |
| `cli SUBCOMMAND…` — run `openclaw …` on the gateway host | SSH | The `openclaw` admin CLI mutates server-side state (agents, cron, sessions, skills, hooks). Per principle §1, all mutation lives behind `clawctl cli`. SSH is the only transport that reaches the host's `openclaw` binary; the wrapper prefers `clawctl-remote` so argv is passed as a string slice (no shell concatenation, no injection surface — see US-005 in `prd.json`). | A "POST /admin/*" gateway endpoint would require building, securing, and rate-limiting a parallel admin API. SSH plus a host-side wrapper is simpler and inherits the host's existing auth (SSH keys + sudoers). | Building a second auth and audit plane on the gateway just to mutate state — and shell-injection via concatenated argv when `clawctl-remote` is missing on the host. | `0`, `2`; downstream `openclaw` exit code on success-path failure |
| `verify {commit,pr,issue,file}` — claim verification | Local (`git`, `gh`, filesystem) | R-2 verification answers "does this artifact exist?" before an agent's claim is accepted. The artifacts (commits, PRs, issues, files) live in `git` and GitHub, not on the gateway — the gateway has nothing to contribute. Local-only also means `verify` works offline against working-tree state. | Routing verification through the gateway would couple verification to gateway uptime and add a network hop to a check that's already authoritative locally. | False-negative verification when the gateway is down but the artifact actually exists in `git`/GitHub. | `0` verified, `1` not found, `2` usage/ambiguous |
| `trace TRACE-ID` — Jaeger UI link + first-30-spans summary | HTTP API (Jaeger, not gateway) | The trace lives in Jaeger, not the gateway. The wrapper hits `$CLAWCTL_JAEGER_UI/jaeger/api/traces/<id>`. No bearer auth (Jaeger is on the operator's intranet); no redaction (span operation/service names are not secret). Read-only by definition. | Routing trace lookups through the gateway would require the gateway to proxy Jaeger — extra surface for zero gain. | Gateway becoming an unnecessary dependency for an observability path that should still work when the gateway is down (the trace-id was the user's escape hatch in the first place — §3). | `0`, `2` (env unset). Downstream Jaeger errors are printed but currently swallowed; tightening this is tracked in US-009. |

## How to use this matrix when adding a subcommand

1. **Identify the operation**: read-only or mutating? If mutating, it goes behind `clawctl cli` and the transport is SSH. Stop.
2. **If read-only**: does the gateway already expose the data via `/v1/*` or `/health`? If yes, use the HTTP API and follow the auth + traceparent + redaction template in `_chat`/`_models_cache`.
3. **If the data lives outside the gateway** (git, GitHub, Jaeger, filesystem): use a local-process call. Do not invent a gateway proxy for it — that re-introduces the failure modes this matrix exists to avoid.
4. **Update this file in the same PR** as the subcommand. A subcommand without a matrix row is a hint that its transport hasn't been justified.
